# 创投智联 Next.js 全栈迁移规格

## Problem Statement

当前项目由用户端 Vite、管理后台 Vite 和独立 Hono API 组成，前端与后端需要分别部署。业务数据仍依赖项目目录中的 SQLite 文件，BP 文件写入本地目录；这种结构适合本地 MVP，但不适合作为 Vercel 上的单项目生产部署，也会带来跨域、环境变量、持久化和登录状态分散等问题。

用户希望保留当前已经完成的用户端、管理后台 UI 和真实交互，把项目改造成一个可在 Vercel 和普通 Node.js 服务器运行的 Next.js 全栈应用，并且迁移过程可回撤。

## Solution

新增 `apps/next` 作为统一的 Next.js App Router 应用：

- `/` 提供用户端首页和平台功能。
- `/market`、`/organizations`、`/institutions`、`/government`、`/reports`、`/events`、`/industry`、`/login`、`/account` 等提供真实路径页面。
- `/admin` 提供独立的运营管理后台，沿用当前后台 UI 和内页交互。
- `/api/*` 由 Next.js Route Handlers 提供后端接口。
- Supabase PostgreSQL 作为业务数据源，Supabase Auth 作为唯一登录身份源，Supabase Storage 作为 BP 文件存储。
- 当前 SQLite 数据通过幂等、可回滚的迁移流程导入 Supabase；原有应用和 SQLite 文件在新版本验证完成前保留。

同一套 `apps/next` 代码支持：

- Vercel 单项目部署。
- 普通服务器的 Node.js `build` 与 `start` 部署。

## User Stories

1. 作为普通用户，我希望通过同一个域名访问平台首页，以便不需要区分多个前端地址。
2. 作为项目方，我希望通过真实路径浏览投融资、公司、创投机构和政府对接页面，以便刷新或分享链接后仍能打开正确内容。
3. 作为投资机构，我希望通过真实路径查看项目和资讯，以便浏览器前进、后退和刷新行为稳定。
4. 作为 FA 机构，我希望在自己的身份和权限下使用平台功能，以便不会看到不属于自己的管理内容。
5. 作为政府招商用户，我希望使用政府对接功能，以便查看并提交产业对接需求。
6. 作为普通用户，我希望注册、登录和完成邮箱验证码验证，以便安全使用平台。
7. 作为已登录用户，我希望刷新页面后会话仍然有效，以便不会频繁返回登录页。
8. 作为未登录用户，我希望访问需要权限的功能时得到明确的登录引导，以便知道下一步如何操作。
9. 作为平台管理员，我希望从 `/admin` 进入独立后台，以便后台与普通用户界面清晰区分。
10. 作为平台管理员，我希望后台菜单和内页保留当前已确认的视觉风格，以便迁移不造成界面倒退。
11. 作为平台管理员，我希望看到运营总览、主体审核、身份内容审核、项目与 BP、政府联系人、对接线索、资讯管理和审计安全模块，以便完成日常运营。
12. 作为平台管理员，我希望后台操作依据真实 Supabase 会话授权，以便浏览器不能伪造管理员身份。
13. 作为审核员，我希望只看到被授予的审核模块，以便最小化后台权限范围。
14. 作为超级管理员，我希望拥有完整的后台管理和审计权限，以便维护平台安全。
15. 作为项目方，我希望提交项目后能在后台审核队列中出现，以便平台管理员可以处理。
16. 作为投资机构，我希望申请查看 BP 后由服务端校验权限，以便项目资料不会被越权读取。
17. 作为项目方，我希望 BP 文件上传到持久化存储，以便部署或重启服务后文件仍然存在。
18. 作为管理员，我希望后台可以管理资讯状态，以便控制草稿、发布和下架。
19. 作为管理员，我希望政府联系人和对接线索的新增、搜索、筛选、跟进交互保持可用，以便日常业务不受迁移影响。
20. 作为用户，我希望收藏、最近浏览、通知和个人中心数据与登录账号绑定，以便跨页面保持一致。
21. 作为平台管理员，我希望审计日志记录关键操作，以便定位数据修改和权限行为。
22. 作为平台所有者，我希望现有 SQLite 数据可以迁移到 Supabase，而不是重新手工录入。
23. 作为平台所有者，我希望迁移脚本可以重复执行且不会重复插入数据，以便上线过程可控。
24. 作为平台所有者，我希望迁移失败时保留原 SQLite、旧应用和备份，以便可以快速回退。
25. 作为本地开发者，我希望新应用可以独立启动并访问同源 API，以便不需要同时启动三个前端和后端服务。
26. 作为本地开发者，我希望缓存、日志、截图、导出文件和临时运行数据只写入项目根目录，以便遵守本地存储边界。
27. 作为部署人员，我希望同一构建产物可以部署到 Vercel 或 Node.js 服务器，以便后续切换基础设施不需要重做业务架构。
28. 作为部署人员，我希望生产密钥只存在于 Vercel 或服务器环境变量中，以便不会泄露到仓库。
29. 作为平台所有者，我希望旧的 Vite/Hono 应用在迁移阶段不被删除，以便可以对照验证和回撤。
30. 作为平台所有者，我希望在我确认前不推送代码、不切换 Vercel 生产项目，以便保留发布控制权。

## Implementation Decisions

- 新增独立的 Next.js App Router 全栈应用作为迁移目标；旧用户端、旧管理后台和旧 API 保留，不在迁移初期删除。
- 新应用统一采用同源路径：用户端根路径、管理后台 `/admin`、服务端接口 `/api/*`。
- 将现有 hash 路由转换为 Next.js 页面路由，保留页面可见内容、交互和视觉方向，不借迁移机会重新设计 UI。
- 将现有 Hono API 的外部路径、请求参数、响应字段和权限语义作为兼容契约，迁移到 Next.js Route Handlers；只有在 Next.js 服务端会话需要时增加必要的内部适配。
- 业务数据从 SQLite 迁移到 Supabase PostgreSQL。迁移覆盖组织、用户、成员关系、项目、BP 授权、联系人、对接线索、资讯、审核、通知、收藏、最近浏览和审计等现有业务实体。
- 迁移脚本必须具备幂等性、事务边界、来源记录和 dry-run 能力；不自动删除 SQLite 数据或覆盖已有 Supabase 数据。
- Supabase Auth 作为唯一线上身份来源。注册、登录、邮箱验证码、密码恢复、会话刷新和退出均由 Supabase Auth 处理；业务角色、组织关系、审核状态和管理员角色由业务表维护。
- 管理员 API 不再信任固定的浏览器请求头；所有后台页面和 `/api/admin/*` 接口都从服务端会话读取用户，并校验管理员角色和模块权限。
- BP 文件迁移到 Supabase Storage。业务表保存文件标识、对象路径、版本、授权范围和有效期；下载必须经过服务端的组织权限、授权状态和有效期校验。
- 本地开发使用项目根目录的环境文件和运行目录；生产环境只使用 Vercel 或 Node.js 服务器的环境变量。服务角色密钥不能进入浏览器包、仓库或截图。
- 新应用不得使用静态导出，必须支持 Next.js 服务端运行，以承载认证、权限、API 和文件授权流程。
- Vercel 使用 `apps/next` 作为 Root Directory；普通服务器使用同一应用的生产构建和 Node.js 启动命令。
- 迁移期间旧应用继续作为回撤基线，只有在新应用的本地验收和用户确认后才考虑删除或改变 Vercel 生产入口。
- 本次不发布 GitHub Issue；本文件是项目根目录内的本地规格记录。

## Testing Decisions

- 以运行中的新 Next.js 应用作为最高验证接缝，优先验证外部行为，不测试内部组件实现细节。
- 浏览器验收覆盖：首页和真实路径导航、登录/注册/邮箱验证码、刷新后的会话保持、普通用户权限、管理员登录和后台路由守卫。
- 浏览器验收覆盖后台核心交互：总览、主体/身份审核、项目和 BP、政府联系人、对接线索、资讯管理、审计日志、通知和表单提交。
- 浏览器验收覆盖数据边界：未登录访问受保护资源、普通用户访问管理员资源、跨组织项目和 BP 访问、过期授权和未授权下载必须被拒绝。
- 浏览器验收覆盖文件流程：BP 上传到 Supabase Storage、授权后下载、撤回或过期后不能继续下载。
- 数据迁移以 dry-run、事务回滚和重复执行作为行为验证重点；验证迁移前后实体数量、关键关联和权限数据一致。
- 执行 Next.js 类型检查和生产构建，确认所有真实路径、Route Handlers、服务端组件和客户端组件能够打包。
- 在桌面和移动视口各检查一次，确认全站 UI 没有横向溢出，后台布局和表单仍可操作。
- 保留旧应用作为回撤验证基线；新应用未通过验收时，不修改旧应用的启动方式和数据文件。

## Out of Scope

- 不在本次迁移中重新设计用户端或管理后台 UI。
- 不删除旧的 Vite 用户端、Vite 管理后台、Hono API 或原 SQLite 文件。
- 不新增与现有平台无关的业务模块、营销页面或数据产品。
- 不接入未经授权的第三方投融资数据源，不把外部爬虫作为迁移前提。
- 不在本次范围内配置正式域名、DNS、CDN、企业 SMTP 或服务器面板；只保证代码结构兼容这些部署方式。
- 不把服务端密钥写入源码、示例截图、提交信息或前端公开变量。
- 不在用户确认前提交、推送、发布或切换 Vercel 生产部署。

## Further Notes

- 当前项目本地 SQLite 和 BP 文件是迁移来源，不是线上持久化方案。
- Supabase PostgreSQL、Auth 和 Storage 是生产主链路；本地生成文件和缓存仍然遵守“只放项目根目录”的约束。
- 如果迁移中发现某个旧接口无法一比一映射，优先增加兼容适配层，不直接改变前端已使用的接口语义。
- 迁移完成后的 Vercel 单项目部署和 Node.js 服务器部署共用同一套 `apps/next` 代码，差异仅限于环境变量、启动方式和反向代理配置。
